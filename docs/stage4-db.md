# Этап 4: база данных преподавателей и зашифрованного чата

Миграция: `supabase/migrations/20261108100000_journal2_teachers_chat.sql`.
Откат: `supabase/migrations_down/20261108100000_journal2_teachers_chat.down.sql`.
Шифрование: `chat-crypto.js` (браузер и Node 24).
Тесты: `tests/db/teachers_chat.sql` (в `npm run test:db`), `tests/unit/chat-crypto.mjs` (в `npm run test:unit`),
`tests/e2e/chat-rest.mjs` (в `npm run test:e2e`, через настоящий REST).

## 1. Что создаётся

| Объект | Назначение | Клиент (authenticated) |
|---|---|---|
| `chat_keys (user_id pk, public_jwk, key_version ≥ 1, backup, created_at, updated_at)` | открытый ключ (только `kty, crv, x, y`) и резервная копия закрытого под паролем переписки | своя строка: только чтение. Запись — `chat_keys_publish` |
| `chat_threads (id, group_id, student_user_id, teacher_user_id, kind, created_at)`, unique `(group_id, student_user_id, teacher_user_id)` | пара «староста/зам ↔ преподаватель» | чтение — участник живого треда. Создание — `chat_thread_open` |
| `chat_messages (id, thread_id, sender_id, sender_key_version, recipient_key_version, iv, ciphertext, created_at)` | только шифртекст: `iv` 16 знаков base64url (12 байт), `ciphertext` 22…10 923 знака (≤ 8192 байт) | чтение — участник живого треда. Запись — `chat_send` |
| `chat_reads (thread_id, user_id, last_read_at)` | отметка прочтения | своя строка своего живого треда; запись — `chat_mark_read` |
| `lesson_notes (group_id, lesson_date, pair_no, subject, lesson_kind, topic ≤ 200, plan ≤ 4000, updated_by, updated_at)`, pk `(group_id, lesson_date, pair_no, subject)` | тема и план занятия | см. матрицу. `updated_by`/`updated_at` ставит триггер `lesson_notes_touch` |
| `chat_my_thread_ids()` | живые треды вызывающего (для RLS) | execute (отвечает только про себя) |
| `_chat_live(group, student, teacher, kind)`, `_chat_b64u_ok(text, int, int)` | проверка актуальных ролей, формат base64url | закрыто |
| политики преподавателя на `tasks` | внесение, правка, удаление заданий своих дисциплин | см. матрицу |

На всех пяти новых таблицах: RLS, `revoke all` у `public, anon, authenticated`, restrictive «Техработы» (`app_open()`).

**Живой тред** (`_chat_live`) — проверка по ТЕКУЩИМ ролям при каждом запросе: студент-сторона — active-членство
группы `base_role = 'student'` и `extra_role ∈ (headman, deputy)`; сторона преподавателя — active-членство
`base_role = 'teacher_' || kind` и назначение этого вида в группе. Перестал быть старостой/замом или снято
назначение/членство преподавателя — тред пропадает у **обоих**: ни чтения, ни отправки, ни ключа собеседника.
Сообщения остаются в базе зашифрованными; роль вернули — переписка снова видна. Сисадмин в эту проверку не
проходит (в ней нет `is_group_staff`, который пропускает сисадмина).

## 3. RPC — точные сигнатуры

Все `security definer`, `search_path = ''`, execute: `authenticated, service_role`. Ошибка — `raise exception '<код>'`,
код приходит в `error.message`. Общие: `not_authenticated` (28000), `maintenance` (42501, `app_open()` ложно).

| Функция | Возвращает | Кто | Ошибки |
|---|---|---|---|
| `chat_keys_publish(p_public_jwk jsonb, p_backup jsonb, p_reset boolean default false)` | `jsonb {"key_version": int}` | active староста/зам или преподаватель (любой группы) | `forbidden`, `bad_key` (не EC P-256, x/y не 43 знака, есть `d`), `bad_backup` (не `{v:1, kdf:'PBKDF2-SHA256', iter 600000…10000000 целое, salt 22 зн., iv 16 зн., ct 24…2048 зн.}`), `key_mismatch` (другой открытый ключ без `p_reset`) |
| `chat_peer_key(p_thread uuid)` | `jsonb {"user_id": uuid, "public_jwk": {kty,crv,x,y} \| null, "key_version": int \| null}` | участник живого треда | `forbidden` |
| `chat_thread_open(p_group uuid, p_teacher uuid)` | `uuid` (новый или существующий) | active староста/зам группы `p_group` | `forbidden` (не староста/зам этой группы), `not_teacher` (P0002: не active-преподаватель группы с назначением своего вида), `group_closed` |
| `chat_threads_my()` | `table(thread_id uuid, group_id uuid, group_name text, peer_user_id uuid, peer_name text, peer_role text, kind text, last_message_at timestamptz, unread int)` | любой вошедший (пусто, если чатов нет) | — |
| `chat_send(p_thread uuid, p_iv text, p_ciphertext text, p_sender_kv int, p_recipient_kv int)` | `uuid` сообщения | участник живого треда | `forbidden`, `group_closed`, `too_long` (22001, шифртекст > 10 923 знаков = 8192 байт), `bad_message` (22023, не base64url / iv не 12 байт / короче тега), `key_changed` (P0001: версия не текущая у меня или у собеседника, или у кого-то нет ключей), `rate_limited` (P0001: ≥ 30 своих сообщений за минуту) |
| `chat_mark_read(p_thread uuid)` | `void` | участник живого треда | `forbidden` |
| `teacher_group_stats(p_group uuid)` | `jsonb {"students": int, "attendance_pct": numeric \| null, "absences_week": numeric}` | преподаватель с назначением в группе, сисадмин | `forbidden` |

Подробности:
- `chat_keys_publish`: первый вызов → версия 1; повтор без сброса с тем же `x, y` → меняется только копия (смена
  пароля переписки), версия та же; `p_reset = true` → новый ключ и копия, версия + 1. В базу пишутся только
  перечисленные поля (лишние отбрасываются). Создание и сброс пишут `audit_log` (`chat_key_publish`, `group_id` null —
  видит только сисадмин; без ключей).
- `chat_threads_my`: живые треды; старосте/заму — ещё строки с `thread_id = null` для каждого active-преподавателя
  его групп (с назначением своего вида), с кем треда нет. `peer_role` ∈ `headman | deputy | teacher_lecture |
  teacher_practice`. `peer_name`: преподавателю — «Староста 24ДММ-2» / «Зам. старосты 24ДММ-2»; старосте —
  «Преподаватель лекций» / «Преподаватель ПЗ». `unread` — сообщения собеседника позже моего `last_read_at`.
  Сортировка: группа, вид, имя.
- `chat_send`: версии проверяются с блокировкой `for share` строк ключей (сброс ключа не «проскочит» между проверкой
  и вставкой); лимит считается под advisory-блокировкой отправителя. Уведомление второму участнику: `kind = 'chat'`,
  `title = 'Новое сообщение в чате'`, `body` = «Староста <группа>» / «Зам. старосты <группа>» / «Преподаватель»,
  `ref = {"thread_id"}`, `dedupe_key = chat:<thread>:<получатель>:<floor(epoch/300)>` — не чаще одного на тред и
  получателя в 5-минутном окне. Ничего из сообщения (даже длины) в уведомление не попадает.
- `chat_mark_read`: `last_read_at = now()` и гасит свои непрочитанные уведомления `chat` этого треда.
- `teacher_group_stats`: «сегодня» по Минску; окно 30 дней включая сегодня. `students` — записей `students` группы.
  План = пары `schedule_lessons` дисциплин и видов вызывающего × 2 ч × `students`; пропуски — все часы (и
  уважительные) тех же дисциплин и видов. `attendance_pct = round(100 × (1 − пропуски/план), 1)`, не ниже 0;
  `null`, если пар не было. `absences_week` — часы за 7 дней. Сисадмин без своих назначений — по всем назначениям
  группы. ponytail: пара подгруппы считается на всю группу, сегодняшние ещё не прошедшие пары входят в план.

## 4. Чат: модель угроз

Сквозное шифрование выполняет `chat-crypto.js` в браузере. Параметры: ECDH P-256; ключ треда HKDF-SHA256
(salt = id треда, info = `journal-chat-v1`) → AES-GCM-256; iv 12 байт случайный; additionalData =
`thread_id|sender_id|sender_key_version|recipient_key_version`. Резервная копия закрытого ключа: AES-GCM-256 с ключом
PBKDF2-SHA256 (600 000 итераций, соль 16 байт) от пароля переписки (NFC), additionalData =
`journal-chat-backup-v1|<user_id>`. Отпечаток: SHA-256 от `journal-chat-fp-v1|<x>.<y>|<x>.<y>` (ключи по возрастанию
`user_id`), первые 8 hex-знаков «XXXX XXXX».

| Кто | Видит / может | Не видит / не может |
|---|---|---|
| Сервер (PostgREST, RPC), сисадмин журнала | — | ничего из чата: строки `chat_*` и чужие копии ключей закрыты RLS (сисадмин не проходит `_chat_live`), RPC отвечают `forbidden`. Проверено тестами (SQL и REST) |
| Администратор базы (postgres / service_role, бэкапы, логи) | метаданные: кто с кем переписывается (группа, роли), когда, сколько сообщений и какой длины (±16 байт), прочтения; открытые ключи; резервные копии; аудит сбросов ключей | текст сообщений; закрытые ключи — пока не подобран пароль переписки |
| Тот же администратор, активно | удалить, задержать или переставить сообщения; **повторить** сообщение (копия строки в том же треде расшифруется: id и время в additionalData не входят); подобрать пароль переписки по копии офлайн (PBKDF2 600 000 ит. на попытку); **подменить открытый ключ** собеседника (см. ниже); отдать изменённый `chat-crypto.js` (хостинг сайта) | подделать сообщение от участника, перенести его в другой тред или выдать за другого отправителя, изменить версии — расшифровка даст `null` («Сообщение недоступно»); прочитать старые сообщения после сброса ключа |
| Собеседник | всё в своём треде | чужие треды (свой ключ треда: соль = id треда) |
| Бывший староста / снятый преподаватель | — (доступ закрыт по текущей роли) | сохранённые у себя ранее расшифрованные тексты страница не хранит; ключи в IndexedDB остаются, но сервер больше не отдаёт ему шифртексты |

**Подмена ключа (MITM).** Открытый ключ собеседника приходит от сервера (`chat_peer_key`). Тот, кто управляет
базой или API, может отдать каждой стороне свой ключ и пересылать сообщения, перешифровывая их. Защита — отпечаток:
стороны сверяют «XXXX XXXX» вне журнала (кнопка «Сверить», по телефону). При подмене отпечатки у сторон разные.
Ограничения: (1) отпечаток 32 бита (8 hex, по контракту) — защищает от подмены «на лету», но целенаправленный
атакующий может перебором подобрать свой ключ под совпадающий отпечаток (порядка 2³² операций — часы на GPU);
(2) сверка добровольная; (3) после сброса ключа отпечаток меняется — его надо сверить заново. Рекомендация UI:
запоминать отпечаток собеседника в localStorage (это не секрет) и предупреждать, если он изменился.

**Чего шифрование не даёт.** Скрытия метаданных; защиты от вредоносного кода, отданного самим сайтом (общая граница
веб-E2E); прямой секретности (компрометация закрытого ключа раскрывает всю переписку на этой версии ключа); защиты
от повтора/удаления сообщений сервером. Пароль переписки ≥ 8 символов — копия выдерживает перебор только настолько,
насколько силён пароль.

## 6. Решения

1. Доступ к треду — по текущим ролям обеих сторон (`_chat_live`), а не только участника: снятый преподаватель не
   переписывается с действующим старостой и наоборот.
2. `chat_my_thread_ids()` открыта клиентам (её зовут политики), но отвечает только про `auth.uid()`; `_chat_live`,
   принимающая произвольных пользователей, закрыта (иначе — справочник ролей).
3. Ключи заводят только возможные участники чата (active староста/зам или преподаватель).
4. `chat_peer_key` при отсутствии ключей у собеседника возвращает `public_jwk`/`key_version` = `null` (UI: «собеседник
   ещё не открыл чат»), а `chat_send` в этом случае — `key_changed`.
5. Новые коды ошибок сверх контракта: `bad_key`, `bad_backup`, `bad_message`, `not_teacher`, `group_closed`.
6. «До 8 КБ» = 8192 байта шифртекста (10 923 знака base64url); открытого текста — до 8176 байт UTF-8
   (≈ 4000 кириллических знаков). UI стоит ограничить поле, например, 2000 знаками.
7. В копию ключа добавлена additionalData с `user_id`: сервер не подсунет пользователю копию чужого ключа.
8. `chat_mark_read` гасит уведомления `chat` треда в колокольчике.
9. `lesson_notes`: преподаватель читает только свою дисциплину и свой вид (как пишет); сисадмин может и писать
   (как в оценках). Удаление разрешено тем же, кто пишет.
10. Задачи: преподаватель правит только свои; удаляет свои, старосты/зама (по текущей роли автора) и легаси своего
    предмета; чужого преподавателя (в т. ч. практика того же предмета) — нет.
11. `teacher_group_stats` считает и уважительные пропуски (посещаемость = присутствие).

## 7. Риски

- **Отпечаток 32 бита** (п. 4) — по контракту; при желании усилить — показывать 16–20 hex-знаков.
- **Повтор сообщений** администратором базы не обнаруживается (id и время не в additionalData). UI может
  отбрасывать дубли по `iv`.
- **Потеря пароля переписки** = потеря старой переписки (сброс ключа). Это свойство схемы.
- **Метаданные** видны администратору базы (п. 4).
- **Сброс ключа** делает нечитаемыми старые сообщения у обеих сторон; частые сбросы — признак проблемы (видно в `audit_log`).
- **Гонка прочтения**: сообщение, закоммиченное чуть позже `chat_mark_read`, но с `created_at` раньше, считается
  прочитанным (≈ доли секунды; опрос раз в 4 с).
- **Изменение правил absences/tasks** для преподавателей: пропуски и задания **без дисциплины** преподавателям
  больше не видны. Записи старосты без `lesson_kind` (старые или по паре вида «другое») преподаватель и раньше не видел.
- **Откат** удаляет ключи, треды, сообщения и темы занятий безвозвратно.

## 8. Чек-лист деплоя в прод (дополнение к stage1–3)

1. Бэкап `tasks`, `absences` (JSON). Новых данных до миграции нет.
2. Применить миграцию. Она не трогает данные; меняет 5 политик `absences`/`tasks` (раздел 5).
3. Проверить:
   `select tablename, count(*) from pg_policies where schemaname='public' and tablename like 'chat_%' or tablename='lesson_notes' group by 1;`
   — у каждой новой таблицы есть «Техработы» и своя политика;
   `select proname, prosecdef, proconfig from pg_proc where proname like 'chat_%' or proname='teacher_group_stats';` — все `t`, `search_path=""`;
