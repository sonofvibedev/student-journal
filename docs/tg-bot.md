# Telegram-бот для домашки и дедлайнов

Редактор (студент с флагом `can_post_tasks`) заполняет задачу в боте, и она уходит админу **заявкой**. Админ одобряет её в Telegram или в веб-разделе «Заявки», и только после этого запись попадает в `data.json` в GitHub. Записи самого админа публикуются сразу.

Функции: `tg-bot` (вебхук), `tg-requests` (веб-раздел «Заявки» и суточное истечение), `tg-set-task-editor` (выдача права).

## Как это устроено

- **Права.** Флаг `profiles.can_post_tasks` у обычного пользователя. Выдаёт и снимает только админ, через `tg-set-task-editor` (проверка по токену GitHub, как в `journal-save`). Сам студент флаг не изменит.
- **Админ** — Telegram-id из секрета `TG_ADMIN_IDS` (один или несколько). Решения по заявкам принимаются только от них, проверяется `callback_query.from.id`, а не чат. Чужие нажатия получают «Нет прав». Привязка аккаунта админу для решений не нужна. Чтобы писать записи сразу (без заявки), админ должен быть привязан.
- **Привязка Telegram.** В кабинете вызывается RPC `tg_create_link_code()` и возвращает код `ABCD-EFGH` (10 минут, одноразовый). Пользователь шлёт код боту (`/start КОД` или просто код). Без привязки бот ничего не делает.
- **Диалог:** `/start` → Домашка / Дедлайн → предмет → дата (ближайшие занятия + «Другая дата», `ДД.ММ`) → текст → предпросмотр. У редактора кнопка «Отправить на проверку», у админа «Сохранить». Состояние диалога в `tg_dialog_state`, 30 минут.
- **Заявка** (`tg_task_requests`): автор, время, тип (ПЗ/УСР для домашки), предмет, дата, текст. Админам приходит «<ФИО из журнала> хочет внести домашку…» с кнопками «Одобрить», «Отклонить», «Отклонить с причиной» (причина — следующее сообщение админа). Если похожая запись или заявка (тот же предмет и дата, текст совпал/вложен/Жаккар не ниже 0,6) уже есть, в сообщении есть пометка про возможный дубль.
- **Решения:**
  - «Одобрить»: запись вносится в `data.json` (поля как у админки + `author` = student_id, `source: "bot"`, `createdAt`, `approvedBy`), автору приходит «Админ одобрил, запись добавлена».
  - «Отклонить»: ничего не вносится, автору приходит «Админ отказал» (+ причина).
  - Автор может «Отозвать» заявку, пока она на проверке. Заявка без решения 7 суток закрывается как «истекла», автор получает уведомление.
- **`/мои`.** Редактор видит свои последние заявки со статусом (на проверке, одобрено, отклонено, отозвана, истекла). Готовые записи правит и удаляет только админ. Админ видит заявки на проверке (с кнопками) и последние записи журнала с «Изменить текст»/«Удалить».
- **Лимиты:** 20 заявок/записей в час на пользователя; не больше 5 заявок на проверке от одного автора; 5 неверных кодов привязки за 10 минут блокируют ввод кода на 10 минут.
- **Журнал** (`tg_action_log`): `request_created`, `approved`, `rejected`, `withdrawn`, `expired`, `admin_direct`, `approve_failed` — кто, что, когда. Читает только service_role. В логах функций нет токенов и текстов задач.

### Схема статусов и сбой GitHub

```
pending ──claim──▶ approving ──commit──▶ approved
   │                  └──rollback (GitHub не принял запись)──▶ pending
   ├─reject─▶ rejected   ├─withdraw─▶ withdrawn   └─expire (7 суток)─▶ expired
```

Каждый переход — один условный `UPDATE … WHERE status = <из> RETURNING`, поэтому двойное нажатие и гонка двух админов решённую заявку не меняют: второй получает «Уже решено: …». В `data.json` пишут только после успешного `claim`, и id записи назначается в момент `claim` (хранится в `record_id`). Если запись в GitHub не удалась, заявка откатывается в `pending`, админ видит «Не вышло внести, повторите» и может нажать «Одобрить» снова. Если функция оборвалась между `claim` и `commit` (заявка осталась в `approving`), через 2 минуты «Одобрить» подхватит её: запись с тем же id уже могла попасть в файл, тогда повторно она не добавляется, а заявка просто становится `approved`.

### Истечение

Два уровня. Ленивый: каждый `/start`, `/мои`, отправка заявки и открытие списка в вебе закрывают просроченные заявки. Суточный: pg_cron в 06:10 UTC (09:10 по Минску) вызывает `tg-requests` с `{"action":"cron-expire"}` и заголовком `x-cron-secret` (секрет `CRON_SECRET` из Vault `cron_secret` — тот же, что у `send-reminders`), чтобы авторы получили уведомление, даже если в бот никто не заходил. Повторные вызовы безопасны: переход `pending → expired` происходит один раз, уведомление уходит только с ним.

## Секреты (что нужно от вас)

| Секрет | Что это |
|---|---|
| `TELEGRAM_BOT_TOKEN` | уже есть |
| `TG_WEBHOOK_SECRET` | длинная случайная строка (`openssl rand -hex 32`), символы `A-Z a-z 0-9 _ -` |
| `GITHUB_TOKEN` | fine-grained токен, только репозиторий `sonofvibedev/student-journal`, право **Contents: Read and write**. Не ваш `gh_pat` |
| `TG_ADMIN_IDS` | числовые Telegram-id админов через запятую (узнать у @userinfobot). Без них заявки некому одобрять |
| `CRON_SECRET`, `SITE_URL` | уже есть (их использует `send-reminders`) |
| `GITHUB_REPO`, `GITHUB_BRANCH` | необязательно; по умолчанию `sonofvibedev/student-journal` и `main` |

```bash
supabase secrets set TG_WEBHOOK_SECRET=<случайная_строка> GITHUB_TOKEN=<токен> TG_ADMIN_IDS=<id1,id2>
```

## Запуск по шагам

1. Применить миграции `20261101130000_tg_bot_tasks.sql` и `20261101140000_tg_task_requests.sql` (`supabase db push`). Вторая ставит cron: в Vault должен лежать `cron_secret` (как для напоминаний), а адрес проекта в `url` внутри файла должен быть вашим.
2. Задать секреты (выше).
3. Задеплоить функции (JWT у них выключен: Telegram его не шлёт, админы доказывают права токеном GitHub):
   ```bash
   supabase functions deploy tg-bot --no-verify-jwt
   supabase functions deploy tg-requests --no-verify-jwt
   supabase functions deploy tg-set-task-editor --no-verify-jwt
   ```
4. Включить вебхук (значения подставьте свои, в репозиторий их не кладите):
   ```bash
   curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook" \
     -d "url=https://<PROJECT_REF>.supabase.co/functions/v1/tg-bot" \
     -d "secret_token=<TG_WEBHOOK_SECRET>" \
     -d 'allowed_updates=["message","callback_query"]' \
     -d "drop_pending_updates=true"
   ```
   Проверка: `curl "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/getWebhookInfo"` — без `last_error_message`.
5. По желанию — меню команд:
   ```bash
   curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setMyCommands" \
     -d 'commands=[{"command":"start","description":"Добавить задачу"},{"command":"my","description":"Мои заявки и записи"},{"command":"cancel","description":"Отмена"}]'
   ```
6. Админ должен один раз написать боту `/start` (иначе Telegram не даст боту написать ему первым).

## Выдать и снять право

```bash
curl -X POST "https://<PROJECT_REF>.supabase.co/functions/v1/tg-set-task-editor" \
  -H "Content-Type: application/json" -H "apikey: <ANON_KEY>" \
  -d '{"ghToken":"<gh_pat>","action":"set","studentId":"st-...","value":true}'
# список имеющих право: {"ghToken":"...","action":"list"}
```

Либо SQL: `update public.profiles set can_post_tasks = true where student_id = 'st-...';`. Снятый флаг действует сразу. Отвязка: `sb.rpc('tg_unlink')`, статус: своя строка в `tg_links`.

## Контракт `tg-requests` (для раздела «Заявки» в вебе)

`POST https://<PROJECT_REF>.supabase.co/functions/v1/tg-requests`, заголовки `Content-Type: application/json` и `apikey: <ANON_KEY>`. Админ определяется по `ghToken` (тот же `gh_pat`); JWT студента не используется. Ответы с `error` приходят с HTTP-кодом 4xx/5xx.

**Список**

```jsonc
// → { "ghToken": "...", "action": "list" }
// ← 200
{
  "ok": true,
  "pending": [{                       // pending и approving, старые первыми
    "id": "uuid", "author": { "student_id": "st-1", "name": "Иванов Иван" },
    "kind": "homework",               // или "deadline"
    "subtype": "ПЗ",                  // ПЗ | УСР | null (у дедлайна)
    "subject": "Эконометрика", "due_date": "2026-11-05", "text": "…",
    "status": "pending",              // или "approving" (идёт внесение: кнопки скрыть)
    "created_at": "2026-11-01T10:00:00+00:00",
    "duplicate": null                 // "record" | "request" | null — возможный дубль
  }],
  "recent": [{                        // последние 20 решённых
    "id": "uuid", "author": { … }, "kind": "…", "subtype": "…", "subject": "…", "due_date": "…", "text": "…",
    "status": "approved",             // approved | rejected | withdrawn | expired
    "created_at": "…", "decided_at": "…",
    "decided_by": "admin",            // "admin" | "author" | "system" | null
    "reject_reason": null, "record_id": "hw-1793…"
  }]
}
```

**Одобрить** `{ "ghToken": "...", "action": "approve", "id": "uuid" }`
- 200 `{ "ok": true, "status": "approved", "record_id": "hw-…" }` (запись в `data.json` внесена; на сайте появится через 1–2 минуты)
- 404 `{ "error": "not_found" }`
- 409 `{ "error": "already_decided", "status": "rejected|withdrawn|expired|approved|approving" }`
- 502 `{ "error": "github_failed" }`: запись не внесена, заявка снова `pending`, можно повторить

**Отклонить** `{ "ghToken": "...", "action": "reject", "id": "uuid", "reason": "необязательно, до 200 символов" }`
- 200 `{ "ok": true, "status": "rejected" }`; 404 и 409 как выше

Общие ошибки: 403 `not_admin` (токен не подходит), 400 `bad_request`. Решение из веба обновляет сообщение админа в Telegram и уведомляет автора; решение из бота видно в следующем `list`. Суточный вызов `{"action":"cron-expire"}` требует заголовок `x-cron-secret`, из браузера его не вызывают.

## Как проверить

1. `node tools/test-tgbot.js` — логика (даты, лимиты, дубли, переходы статусов, права, истечение, права в миграции).
2. Без заголовка: `curl -X POST https://<PROJECT_REF>.supabase.co/functions/v1/tg-bot -d '{}'` → `403`.
3. **Заявка.** Выдать флаг редактору, привязать его, пройти `/start` до «Отправить на проверку». Автору: «Отправлено админу на проверку»; админу приходит сообщение с кнопками; в `/мои` у автора статус «на проверке».
4. **Одобрение.** Нажать «Одобрить»: сообщение админа меняется на «Одобрено, внесено», автору приходит уведомление, в репозитории коммит `Бот: домашка …`. Повторное нажатие даёт «Уже решено».
5. **Отказ.** Новая заявка → «Отклонить с причиной» → написать причину: автору придёт «Админ отказал» с причиной, в `data.json` ничего нет.
6. **Отзыв.** Новая заявка → у автора в `/мои` «Отозвать»: сообщение админа становится «Автор отозвал».
7. **Истечение.** Для проверки сдвинуть дату: `update tg_task_requests set created_at = now() - interval '8 days' where id = '…' and status = 'pending';`, затем `/мои` (ленивое истечение) или `curl -X POST …/tg-requests -H "x-cron-secret: <CRON_SECRET>" -d '{"action":"cron-expire"}'`. Заявка станет `expired`, автор получит сообщение.
8. Сбой GitHub: временно задать неверный `GITHUB_TOKEN`, нажать «Одобрить» — «Не вышло внести, повторите», заявка осталась `pending`.

## Ограничения и риски

- **Запись видна не сразу:** `data.json` отдаёт GitHub Pages, обновление 1–2 минуты после коммита.
- **Админ перезаписывает записи бота,** пока клиент не слит с удалённой версией: `saveDataToGitHub` берёт свежий `sha`, но содержимое строит из копии, загруженной при открытии страницы. Нужна правка в `index.html` (слияние записей `source: "bot"` перед PUT).
- **Расписание:** `schedule.js` читается с сайта как текст и разбирается регулярками. При сбое бот предложит «Сегодня / Завтра / Через неделю» и «Другая дата». Подгруппы и замены не учитываются, зачёты пропускаются.
- Тип «УСР» в форме админки отсутствует (ЛК/ПЗ/ЛР); бот пишет его как есть.
- Если бот не может написать админу (тот не нажимал `/start`, заблокировал бота), ошибка только логируется, заявка остаётся `pending` и видна в `/мои` админа и в вебе.
- Код привязки живёт 10 минут: не показывайте его на экране лишний раз.
