## 2. Решение по входу: оставить Supabase Auth

Остаёмся на Supabase Auth, самописный механизм не вводим. Причины: он уже работает на проде, сессии/JWT проверяются самой базой (`auth.uid()` в RLS), 28 аккаунтов переезжают без смены паролей.

- Студенты: логин + пароль, как сейчас (синтетический email). Новые студенты сами задают логин и пароль (ТЗ), формат тот же. Домен email оставляем прежним, чтобы не перевыпускать 28 аккаунтов.
- Староста новой группы, преподаватели, сисадмин: настоящая почта + пароль. В форме входа одно поле «логин или почта».
- Пароль, 8–72 символа (как сейчас).
- Принадлежность к группе и роль берутся не из `profiles`/jsonb, а из новой таблицы членства (п. 3). `profiles` остаётся как есть (связь аккаунта с `student_id`) и на этапе переезда дополняется `group_id`.

## 3. Схема базы (целевая)

Все новые таблицы: `enable row level security`, права `anon/authenticated` отозваны и выданы точечно. Запись критичных данных только через `security definer`-функции и Edge Functions.

```
groups(id uuid pk, code text unique, name text, faculty, study_form, course, university default 'БГЭУ',
       status text check in ('active','closed','graduated'), warn_hours int default 8, dean_hours int default 12,
       semester_end date, graduated_at, created_at)
group_invites(group_id, code_hash unique, created_at, rotated_at)      -- код группы, 8 символов без 0/O/1/I, хранится хэш
students(id text pk, group_id, last_name, first_name, study_form 'budget'|'paid', claimed_by uuid null unique,
         telegram jsonb, sort, created_at)                              -- id остаётся прежним 'st-…', чтобы не терять app_events и значки
absences(id, group_id, student_id, date, pair, subject, hours, kind, excused bool, certificate_id, created_by, created_at)
certificates(id, group_id, student_id, period, closed_absence_ids[], created_by)
memberships(user_id, group_id, role, status, student_id null, consent_at, consent_version, created_at,
            primary key (user_id, group_id))
            role: student | headman | deputy | teacher_lecture | teacher_practice | sysadmin
            status: pending | active | rejected | removed
registration_requests(id, owner_user_id, status draft|submitted|approved|rejected, step, payload jsonb, schedule_status, reviewed_by, reviewed_at)
join_attempts(ip_hash, group_code_hash, at)                            -- блок 5 неверных кодов на 15 минут
consents(user_id, version, accepted_at, text_hash)
audit_log(id, at, actor, group_id, action, details jsonb)              -- логи для сисадмина
```

Правила (CHECK + частичные unique-индексы): один староста и один заместитель на группу; одна запись `students` занята максимум одним аккаунтом (`claimed_by unique`); пользователь не может иметь двух активных членств в одной группе.

**Хелперы RLS** (`security definer`, `stable`, `set search_path=''`):
- `my_active_groups()` — группы, где я `active`;
- `has_role(group, roles[])`;
- `is_sysadmin()`;
- `group_open(group)` — `groups.status='active'` и режим техработ выключен или я староста/сисадмин (замена `app_open()`).

**Политики (основные).**
- `pending` читает: ничего из данных группы. Только свою строку в `memberships` и `students` с `claimed_by = me` (чтобы показать экран ожидания). Данные закрыты в политиках, не в интерфейсе.
- Студент `active`: читает данные своей группы; пишет только своё (подписки, профиль). Пропуски не вносит.
- Староста/заместитель: читает и пишет данные своей группы; подтверждает/сбрасывает привязки, выдаёт справки. Ролей не меняет.
- Преподаватель: читает только свои дисциплины и свой вид занятий (таблица `teacher_assignments(user_id, group_id, subject, kind)`).
- Сисадмин: все группы.
- `group_open()` в `with check` на запись: журнал закрыт = только просмотр.

## 4. Перенос 24ДММ-2 (без повторной регистрации)

Порядок (всё сначала на копии, прод только по вашей команде):

1. Бэкап: `pg_dump` + выгрузка таблиц в JSON, проверка, что файл читается и числа совпадают. Внутри базы уже есть `backup_20261103_*`; сверх этого делаем новые.
2. Миграция `up`: создать таблицы, вставить группу «24ДММ-2» (БГЭУ), развернуть `journal_private.students` в `students` (28), `absences` в `absences` (276), `isAdmin` в `memberships.role='headman'`, все 28 из `profiles` в `memberships(active)`. `profiles.student_id` и `students.id` не меняются: `app_events`, `student_achievements`, `game_records` продолжают работать. В таблицы с данными студентов добавляется `group_id` (заполняется id 24ДММ-2).
3. `journal_private` не удаляется и не меняется. Остаётся как страховка до отдельной команды.
4. Отчёт сверки (`docs/reports/migration-24dmm2.md`): число студентов, пропусков, событий, значков, игровых рекордов, задач, профилей до и после; хэш содержимого по каждой таблице.
5. `down`-скрипт к каждой миграции. Откат проверяется на копии: после `down` отчёт сверки даёт те же числа.
6. Согласие запрашивается при первом входе после обновления (дата + версия сохраняются).

**Опасное место:** клиент читает `journal_private` напрямую и определяет `isAdmin` из jsonb, а `journal-save` пишет массив целиком. Нельзя просто убрать таблицу. План: переписываем чтение на новые таблицы и функции за один этап с переходной view `journal_private_compat` для старых вкладок. Старый `journal-save` в этот период блокируется, пока админка на новом API (иначе потеряются записи).

**`data.json` и зеркало задач.** Публичный `data.json` в GitHub не подходит для нескольких групп. После переезда задачи читаются из БД по RLS. `data.json` остаётся только для старых вкладок и замораживается (решение зафиксируем в `DECISIONS.md`).

**Telegram.** `tg_links` получает `group_id`. Сброс привязок: функция для сисадмина + экран «Журнал обновился» с кодом на 10 минут + рассылка ботом (бот пишет по `chat_id`, он сохранён). Админ бота сейчас определяется через секрет `TG_ADMIN_IDS`; в 2.0 староста группы определяется по членству.

## 7. Риски

1. **Перенос единственных прод-данных.** Смягчение: бэкап с проверкой чтения, `down`, репетиция на копии, прод только по вашей команде. Режим техработ уже включён, окно есть.
2. **Нет тестового стенда в Supabase.** Free-план: 2 активных проекта, оба заняты (`journal-24dmm2`, `shtab`). Нужен выбор (см. вопросы).
3. **Скрейпинг bseu.by:** хрупкая разметка, возможны блокировки. Смягчение: при ошибке остаётся прошлая версия, подпись «по данным bseu.by».
4. **Письма сисадмину и старосте на почту:** нужен почтовый провайдер и ключ в секретах Edge Functions (не в репозитории).
5. **Шифрование чата** (этап 4): потеря закрытого ключа = потеря истории. Резервная копия ключа под паролем в ТЗ; реализует Opus.
6. **Большой клиент (`index.html`, 7285 строк, `isAdmin` ×11):** правки точечные, иначе регресс в рабочем журнале.
7. **Разрастание функций с service-ключом:** каждая проверяет роль и группу по JWT; общий helper `requireRole(req, group, roles)` вместо копипасты.
