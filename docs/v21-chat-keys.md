## Что видит пользователь

Открыл «Чат» — переписка открыта. Ничего вводить не нужно.
- Первый раз на устройстве: «Готовим шифрование на этом устройстве…», строка «Ключ создаётся…» (доли секунды).
- Собеседник ещё ни разу не открывал чат: поле ввода выключено, «Собеседник ещё не открывал чат».
- Новое устройство того же человека (второй телефон, очищенный браузер), а прежнее живо: «Ждём подтверждения этого
  устройства — откройте чат на устройстве, где уже переписывались». Прежнее устройство при следующем открытии чата само
  передаёт ключи, новое через несколько секунд читает всю историю. Кнопка «Нет доступа к прежнему устройству».
- «Начать заново на этом устройстве» (из ожидания или из «Сверить»): прежние устройства отзываются, переписка до этого
  момента на этом устройстве не читается («Сообщение недоступно на этом устройстве: ключ был заменён»), новые сообщения — да.
- Собеседник сменил устройство: заметная карточка «Ключ собеседника заменён» (или «У собеседника новое устройство»)
  с новым отпечатком и «Понятно». Отпечаток всегда в строке шифрования и в «Сверить».

## Протокол

| Что | Как |
|---|---|
| Ключ устройства | ECDH P-256, `generateKey(extractable = false)`; закрытый — неизвлекаемый `CryptoKey` в IndexedDB (`journal-chat`/`keys`, запись `dev:<user_id>`). На сервер — только `{kty, crv, x, y}` (`chat_device_register`) |
| Ключ треда | случайные 32 байта «эпохи» (`chat_threads.key_epoch`). Создаёт первое устройство, открывшее тред, когда у обоих участников есть хотя бы одно устройство |
| Обёртка ключа эпохи для устройства T, сделанная устройством W | `HKDF-SHA256(ECDH(W, T), salt = '<thread>\|<epoch>', info = 'journal-chat-wrap-v2\|W\|T')` → AES-GCM-256; iv 12 байт; AAD `journal-chat-wrap-v2\|thread\|epoch\|W\|T` → `chat_thread_keys` |
| Сообщение | AES-GCM ключом эпохи; iv 12 байт; AAD `journal-chat-v2\|thread\|epoch\|sender_id\|sender_device` → `chat_messages(key_epoch, sender_device, iv, ciphertext)` |
| Отпечаток | SHA-256 `journal-chat-fp-v2\|<uid>:<x.y действующих устройств, по возрастанию>\|<uid>:…` (участники по `user_id`), 16 hex «XXXX XXXX XXXX XXXX» (64 бита вместо прежних 32) |
| Новое устройство | `chat_wraps_add`: обёртки выдаёт только действующее устройство **того же аккаунта** и только эпох, ключ которых у него есть |
| Новая эпоха | `chat_epoch_create`, только если текущая «устарела» (`_chat_epoch_stale`): ключа нет, среди получателей есть отозванное устройство, или у участника не осталось действующего устройства с ключом. Обёртки — ровно на все действующие устройства обоих (`devices_changed` иначе), номер = текущий + 1 (`epoch_conflict` — кто-то успел раньше, клиент перечитывает) |
| Отправка | `chat_post(thread, device, epoch, iv, ct)`: эпоха текущая и не устаревшая, у устройства есть её ключ (`key_changed` иначе); лимит 30/мин, 8 КБ, уведомление — как `chat_send` |

RPC: `chat_device_register(jsonb)`, `chat_device_reset(uuid)`, `chat_thread_state(uuid, uuid)`, `chat_epoch_create(uuid, uuid, int, jsonb)`,
`chat_wraps_add(uuid, uuid, jsonb)`, `chat_post(uuid, uuid, int, text, text)` — все `security definer`, `search_path = ''`,
участник живого треда (`chat_my_thread_ids`, как в этапе 4) и своё действующее устройство (`forbidden`, `device_revoked`).
Таблицы `chat_devices`, `chat_thread_keys`: RLS, `revoke all` у клиентов, «Техработы»; прямого доступа нет, только RPC.
Устройства заводят только active староста/зам и преподаватели; до 10 действующих и 50 всего на человека (`too_many_devices`).

## Модель угроз (что изменилось)

| Кто | Видит / может | Не видит / не может |
|---|---|---|
| Утечка базы / бэкапа, администратор БД пассивно | метаданные (кто, с кем, когда, размер), открытые ключи устройств, обёртки, шифртексты | текст, ключи тредов. Подбирать нечего: пароля больше нет, обёртки открываются только закрытым ключом устройства |
| Сервер активно (злонамеренный админ, взлом API) | добавить человеку «своё» устройство → (а) свои устройства этого человека автоматически выдадут ему ключи; (б) собеседник при новой эпохе обернёт ключ и для него. Удалить/задержать/повторить сообщения. Отдать изменённый `chat-crypto.js` | сделать это незаметно: отпечаток включает все действующие устройства обоих, у собеседника появляется «ключ собеседника заменён / новое устройство», в «Сверить» видно число устройств |
| Бывший участник, снятый преподаватель | — (доступ закрыт по текущей роли, как в этапе 4) | — |

Новые ограничения, честно:
- **Автоподтверждение своих устройств.** Новое устройство получает ключи без вопроса. Сервер, который подсунул вам
  «ваше» устройство, получит и историю. Обнаружение — отпечаток и число устройств в «Сверить» (у себя предупреждения нет,
  только у собеседника). Усилить — одно нажатие «Подтвердить новое устройство?» на прежнем устройстве (без пароля).
- **История отозванных устройств.** Для старых эпох обёрнувшее устройство может быть уже отозвано; его открытый ключ
  отдаёт сервер, и в отпечатке его нет. Сервер, выдумавший такое «старое» устройство, может показать поддельное старое
  сообщение. Писать новое под чужой ключ не получится: ключ текущей эпохи принимается, только если его обернуло действующее устройство.
- **Подпись отправителя.** Ключ эпохи общий у обоих участников: каждый технически может составить сообщение «от имени»
  другого (как и в этапе 4). Сервер — нет.
- **Приватный режим / запрет хранилища.** Ключ устройства живёт до закрытия вкладки; каждое открытие — новое устройство,
  ожидание подтверждения и отметка у собеседника. Потолок 10 устройств, дальше — «Начать заново».

## Вопрос владельцу: история только на устройствах или автоматический бэкап?

Реализовано: **история только на устройствах** (вариант А). Это единственный вариант, при котором сервер действительно
не может прочитать переписку.

| | А. Только на устройствах (сейчас) | Б. Автобэкап под ключом от аккаунта |
|---|---|---|
| Потеряны все устройства | старая переписка пропала; чат продолжается новыми ключами, собеседник видит «ключ заменён» | после входа на новом устройстве история возвращается сама |
| Утечка базы / бэкапа | ничего | ничего, если ключ бэкапа сервер не хранит |
| Злонамеренный сервер / администратор Supabase | не прочитает (см. ограничения выше) | **прочитает**: пароль входа сервер видит при каждом входе (Supabase Auth), значит и ключ, выведенный из него; ключ, который хранит сам сервер, — тем более |
| Смена пароля входа, сброс через «Забыл пароль» | ничего не ломает | бэкап надо перешифровать; сброс пароля = потеря бэкапа (либо сервер хранит ключ — тогда это не E2E) |

Как переключить на Б, если решите: бэкап — это ещё одно «устройство» в `chat_devices` с пометкой `kind = 'backup'`,
его закрытый ключ хранится на сервере, зашифрованным ключом PBKDF2 от пароля входа (пароль берётся на экране входа
в момент входа, до отправки в Supabase). Остальной протокол не меняется: бэкап получает обёртки как любое устройство,
новое устройство после входа разворачивает его и забирает ключи. Объём — одна миграция (колонка + RPC) и правка
`chat-crypto.js`/экрана входа, порядка дня работы.

**Вопрос:** оставить А (сервер не читает, но потеря всех устройств = потеря истории) или включить Б (история не теряется,
но от администратора сервера переписка уже не защищена)?

## Деплой

1. Бэкап не нужен (данных нет), но по порядку: `node tools/backup-tables.mjs pre-chat12 chat_threads,chat_messages,chat_keys`.
2. `node tools/apply-prod.mjs 20261122100000`; проверка: `select proname, prosecdef, proconfig from pg_proc where proname in ('chat_device_register','chat_device_reset','chat_thread_state','chat_epoch_create','chat_wraps_add','chat_post');`
   — все `t`, `search_path=""`; `select has_function_privilege('anon','public.chat_post(uuid,uuid,int,text,text)','execute');` — `f`.
3. `node tools/bump-assets.mjs <N>` (кэш `sw.js` и `?v=` у `chat-crypto.js`/`chat-ui.js`) и выкладка сайта. Старая вкладка до
   обновления будет просить пароль переписки — после обновления экран пароля исчезает.
4. Откат: `node tools/apply-prod.mjs 20261122100000 down` (удалит устройства, обёртки и сообщения новой схемы) + прежний сайт.

## Тестовый преподаватель в проде (делает владелец, без секретов в репозитории)

Сервисный ключ не нужен: у сисадмина уже есть путь. Edge Function `sysadmin-user` создаёт учётную запись со случайным
паролем (`genPassword`) и показывает его один раз; `sysadmin_assign_teacher` назначает. `tools/test/seed-teachers.mjs`
для прода не годится (и правильно: `guard.mjs` его останавливает).

1. Нужны два адреса, доступных владельцу, например `dimpolenyshevv+tlec@gmail.com` и `dimpolenyshevv+tpz@gmail.com`
   (Gmail доставляет «+…» в тот же ящик; писем журнал всё равно не шлёт — почта создаётся подтверждённой).
   Один аккаунт не может быть и лектором, и практиком одной группы (одно членство на группу), поэтому два.
2. `sysadmin.html` → «Роли» → группа 24ДММ-2 → «Преподаватели» → почта, «Ведёт: Лекции», один предмет → «Добавить
   преподавателя» → «Создать и назначить». Пароль покажется один раз: сохраните в менеджер паролей. То же для «ПЗ».
3. Вход преподавателем — в отдельном профиле Chrome (не в инкогнито: там ключ устройства пропадает при закрытии окна),
   согласие → «Чат». Со своего аккаунта старосты: «Чат» → «Лекции» / «ПЗ». Проверить: сообщения в обе стороны, отпечатки
   совпадают; вход старостой со второго устройства → «Ждём подтверждения» → открыть чат на первом → история читается.

Безопасно ли: да, с оговорками. Тестовый преподаватель — настоящая роль: видит ФИО и пропуски группы по своему предмету,
может ставить оценки и задания, которые **уйдут студентам уведомлениями**. В тестовом кабинете трогать только «Чат».
Сообщения в чате видят только двое участников; студентам и сисадмину чат не виден.

Удаление после проверки:
1. «Роли» → «Преподаватели» → «Снять» у обоих: доступ к группе и чату закрывается сразу (тред и сообщения остаются в базе
   зашифрованными, у старосты вкладки пропадают).
2. Supabase Dashboard → Authentication → Users → удалить оба аккаунта. Каскадом уходят членства, назначения,
   устройства преподавателя, треды с ним (`teacher_user_id … on delete cascade`), их сообщения, обёртки и отметки прочтения.
3. Проверка (SQL Editor, только чтение):
   `select (select count(*) from chat_threads) threads, (select count(*) from chat_messages) msgs, (select count(*) from chat_thread_keys) wraps,`
   `(select count(*) from memberships where base_role like 'teacher_%') teachers;` — нули (кроме тредов с настоящими преподавателями, если они уже есть).
   Остаются: ваши устройства старосты в `chat_devices` (только открытые ключи, пригодятся для настоящего чата) и записи
   `audit_log` о создании/снятии — это след, удалять не нужно.
